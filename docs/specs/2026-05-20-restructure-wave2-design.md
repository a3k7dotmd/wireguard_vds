# Волна 2: единый state-файл + CIDR

**Дата:** 2026-05-20
**Статус:** утверждён к реализации
**Предыдущая волна:** [wave 1](./2026-05-20-restructure-wave1-design.md) (выполнена, на master)
**Следующая волна:** добавление подкоманд `list / status / regenerate / export`

## Контекст

После волны 1 у скриптов есть единая точка входа (`wgctl`), но runtime-state сервера всё ещё размазан по четырём отдельным `*.var`-файлам в `/etc/wireguard/`: `endpoint.var`, `dns.var`, `vpn_subnet.var`, `last_used_ip.var`. Это:

1. **Много чтений.** `scripts/add-client.sh` начинается с четырёх `read -r FOO < ./foo.var` подряд — каждый файл по отдельности.
2. **Хрупкий формат `vpn_subnet.var`.** Сейчас файл содержит `10.8.8.` (с trailing dot), и `add-client.sh` конкатенирует это с last octet через `${VPN_SUBNET}${OCTET_IP}`. Хак, который работает, но любой человек, заглянувший внутрь, его не поймёт.
3. **Невозможность атомарной перезаписи.** Поменять три значения одновременно — три `echo`-команды без транзакции.

Волна 2 объединяет state в один файл `state.env` shell-source-формата и переводит подсеть в стандартный CIDR.

## Архитектура

### Формат `state.env`

```sh
# /etc/wireguard/state.env — конфигурация инстанса.
# Перезаписывается целиком при изменениях; не редактируется руками.
ENDPOINT="1.2.3.4:51820"
DNS="9.9.9.9"
VPN_SUBNET="10.8.8.0/24"
LAST_USED_IP=3
```

Один файл, shell-syntax, источаемый через `source` (или `.`). Перезаписывается **целиком** через heredoc при каждом изменении — никаких `sed -i` хаков, никакой частичной согласованности.

### Использование

Сервисные скрипты делают:

```sh
# shellcheck source=/dev/null
. "${WORK_DIR}/state.env"
```

И дальше работают с переменными `${ENDPOINT}`, `${DNS}`, `${VPN_SUBNET}`, `${LAST_USED_IP}`.

При изменении (например, выделили новый IP — `LAST_USED_IP=$((LAST_USED_IP+1))`) — перезапись целиком:

```sh
cat > "${WORK_DIR}/state.env" <<EOF
ENDPOINT="${ENDPOINT}"
DNS="${DNS}"
VPN_SUBNET="${VPN_SUBNET}"
LAST_USED_IP=${LAST_USED_IP}
EOF
```

### CIDR-форма подсети

Старое: `VPN_SUBNET="10.8.8."` (магический trailing dot).
Новое: `VPN_SUBNET="10.8.8.0/24"`.

При генерации клиентского IP в `add-client.sh`:

```sh
IFS=. read -r o1 o2 o3 _ <<<"${VPN_SUBNET%/*}"
prefix="${o1}.${o2}.${o3}"
CLIENT_IP="${prefix}.${LAST_USED_IP}/32"
```

Маска `/24` хардкодится (это уже было — текущая семантика «один октет на клиента»).

## Изменения по файлам

### `scripts/install.sh`
- Удалить четыре отдельные записи (`./endpoint.var`, `./vpn_subnet.var`, `./dns.var`, `./last_used_ip.var`).
- В конце сбора данных (после прохода через `detect-wan.sh`) записать единый heredoc `cat > ./state.env <<EOF ... EOF`.
- В вычислении подсети заменить `echo "${SERVER_IP}" | grep -o -E '([0-9]+\.){3}' > ./vpn_subnet.var` на CIDR-форму: `IFS=. read -r o1 o2 o3 _ <<<"${SERVER_IP}"; VPN_SUBNET="${o1}.${o2}.${o3}.0/24"`.

### `scripts/add-client.sh`
- Удалить четыре `read -r XXX < ./xxx.var` строки.
- Добавить `# shellcheck source=/dev/null` и `. "${WORK_DIR}/state.env"`.
- Переменная `OCTET_IP` переименовать в `LAST_USED_IP` (или оставить как было через присваивание `OCTET_IP="${LAST_USED_IP}"` — выберу второе, чтобы сохранить локальные вычисления нетронутыми).
- Изменить формирование `CLIENT_IP` под CIDR-парсинг (см. выше).
- Заменить финальный `echo "${OCTET_IP}" > /etc/wireguard/last_used_ip.var` на полную перезапись `state.env` со всеми четырьмя полями.

### `scripts/reset.sh`
- Сейчас: `echo "1" > last_used_ip.var`.
- Стало: загрузить state.env, выставить `LAST_USED_IP=1`, перезаписать целиком.

### `scripts/remove-client.sh`
- **Не трогаем.** `remove-client` сейчас не лезет в `last_used_ip.var` и не должен (пользователь явно отказался от переиспользования IP — это [project memory: project-future-directions](../../). Контракт «дырки в пуле допустимы» сохраняется).

## Совместимость

При переустановке через `wgctl install` (которая внутри идёт `uninstall + install + add-client`) `/etc/wireguard/` уничтожается полностью и пересоздаётся. Так что старые `*.var`-файлы автоматически исчезнут. Пользователям с уже запущенным сервером, у которых сейчас стоят `.var`-файлы — придётся либо переустановить, либо сконвертировать руками (одна строка `cat > state.env <<EOF ... EOF`). README документирует, но миграционного скрипта не пишем — это маленький проект, аудитория небольшая.

## Тестирование

`tests/smoke.sh` сейчас покрывает только `remove-client.sh` — он не источает `state.env` и не выделяет IP. Так что **smoke-тесты остаются неизменными**. Покрытие не ухудшается (smoke по-прежнему зелёный после волны 2). Реальное end-to-end тестирование install/add требует VM с root — вне scope локальной верификации, как и в волне 1.

Проверочные пункты после имплементации:
- `make lint` чистый (включая новый источник `. state.env` — корректный shellcheck-directive `source=/dev/null`).
- `make test` зелёный.
- Грep'ом убедиться, что в репо не осталось ссылок на `*.var`: `grep -rn 'endpoint\.var\|dns\.var\|vpn_subnet\.var\|last_used_ip\.var' scripts/ tests/ wgctl Makefile` — пусто.

## Что НЕ входит в волну 2

- **Миграционный скрипт** для существующих установок со старыми `.var`-файлами — не пишем.
- **Параметризация имени интерфейса** (`wg0` → переменная `INTERFACE_NAME`) — захардкожено везде в `wg-quick@wg0`. Это отдельный refactor, не входит.
- **Парсинг существующих `[Peer]`-блоков для свободных IP** — пользователь явно отказался от reuse в [project memory](../../). LAST_USED_IP остаётся монотонным.
- **Новые подкоманды** — волна 3.
- **Pre-existing баг с пустым `SERVER_PRIVKEY` при повторной установке** (reviewer wave 1 заметил в `install.sh:74`) — отдельный fix, не привязан к state-refactor.

## Связь с волной 3

Волна 3 (новые подкоманды `list / status / regenerate / export`) будет работать с `state.env` напрямую — например, `wgctl list` парсит `wg0.conf`, но `regenerate` использует `${ENDPOINT}` и `${DNS}` для пересоздания клиентского конфига, читая их через `. state.env`. Без волны 2 та же логика читала бы из четырёх `.var`-файлов — мелочь, но грязнее.
